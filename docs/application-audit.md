# Whole-application audit and remediation

Audit started 2026-10-02. This register records confirmed defects and verification; pending entries are not claims of completed remediation.

## Architecture and baseline

The public `landing` application prerenders its public routes. The Telegram Mini App lives in `client`; `admin` is a separate React application. The TypeScript `server` owns Telegram authentication, administration, payments, bot workflows, question ingestion, and PostgreSQL/Redis-backed services. In the deployed container, the Go `gateway` accepts public traffic, handles voice signaling itself, and proxies other routes to Node. Consequently, Node-only voice fixes do not protect the deployed Go signaling path. Both runtimes share Prisma-managed PostgreSQL tables, Redis matchmaking, and LiveKit rooms/recording services.

Pre-existing landing work, public statistics work, and the staged directory inventory were preserved before this audit. A private local baseline snapshot records the starting HEAD and file contents. Crawler control files are preserved.

Baseline evidence:

- Landing build and build checks passed: ten public routes and a noindex 404.
- Node unit suite passed: 58 files, 612 tests.
- Go gateway tests passed in all seven internal packages.
- Client initially lacked installed dependencies. Installing its existing lockfile resolved the missing-tool prerequisite. Baseline build/lint then passed with two hook warnings and a 237.54 kB gzip initial JavaScript bundle.
- Admin baseline build/lint passed; a Fast Refresh export warning remains for review.
- Production Telegram, payment, and LiveKit credentials are not used for verification. PostgreSQL/Redis integration checks use isolated loopback services.

## Application-wide review and release boundaries

The review covered the production entry points and shared Node/Go call lifecycle, admission and recording ownership; authentication and signed webhook boundaries; payments/refunds and administrator permissions; PostgreSQL migrations and row-lock ordering; Redis coordination and durable workers; crawler ingestion/filtering; client connection/authentication recovery; admin request/dialog workflows; and public/private frontend delivery. Targeted source searches also checked TODO/FIXME markers, unsafe raw SQL, debug output, empty catches and production dependency paths. No mass cleanup or policy rewrite was performed to make those searches look clean.

Raw row-lock SQL limits table names to a compile-time union and binds record IDs as parameters. Reviewed empty catches include optional cache, audio cleanup/autoplay and notification fallbacks; their presence is not evidence that all those operations are durable. Production payment sequence failures propagate; its local fallback is test-only. LiveKit stop failures are logged by the provider wrapper. Optional quota announcements and other older notification producers remain best effort; durable completion/referral/subscription effects should not be interpreted as a guarantee for every bot announcement.

The public and ordinary-browser launch have actual viewport/navigation/focus checks. The admin review has 27 synthetic screen/viewport accessibility results and workflow checks in `docs/admin-ui-quality.md`; current admin lint/build pass with the existing Fast Refresh warning. Mini App call and moderation recovery has genuine React tests, but no physical Telegram/device/provider journey or accessibility certification is claimed.

Remaining release requirements:

- **B01:** decide calendar-month versus whole-validity included calls/recordings. Existing prices and usage-period behavior remain intact; policy-dependent changes are excluded from this remediation.
- **External staging:** exercise Telegram OTP, Stars purchase/refund, LiveKit voice/microphone behavior, recording start/stop/restart/delayed callbacks, and storage delivery with real staging credentials.
- **Deployment:** rehearse additive migrations and the coordinated legacy worker/crawler cutover against a production-like backup. Remote GitHub CI and a production migration/deployment have not run.
- **Operations:** monitor queue capacity, oldest post-call work, UNCONFIRMED Telegram delivery and pending refunds. An active crawler drain during shutdown is not verified; lease expiration allows later ownership recovery, and interrupted ingestion can require the next scheduled crawl after the visited window. The lifecycle container checks disable external crawler work.
- **Runtime:** the verified production image uses Node 24.21.0 with bundled Undici 7.29.1. The workstation Node 24.19.0 still bundles Undici 7.29.0; use a patched Node runtime for any bare-Node deployment. This audit does not silently replace the user's installed Node executable.

The local test harness now retires its own ACTIVE/PENDING fixtures in `finally`, including deliberate integer-overflow rollback cases. Previous synthetic overflow calls were retired only in the dedicated verification database after ownership checks; preview startup recovery subsequently succeeded. One added binding guard initially rejected Prisma's internally appended pool parameters; it now validates the exact loopback database and only the expected pool options. No production records were cleaned up.

## Reproduce the isolated production checks

Build the current production image with `docker build -t pairtalk-whole-audit:local .`. Use the private loopback bindings and owned PostgreSQL/Redis container names returned by `scripts/start-isolated-services.cjs`; reuse existing verification fixtures rather than creating duplicate services. Bindings must stay outside the checkout and must never be printed or committed.

```text
node scripts/isolated-command.cjs <private-runtime.json> migrate
node scripts/isolated-command.cjs <private-runtime.json> schema
node scripts/isolated-command.cjs <private-runtime.json> integration
node scripts/start-isolated-container.cjs <private-runtime.json> <owned-postgres-container> <owned-redis-container>
node scripts/check-isolated-container.cjs <private-container-verification.json>
node scripts/check-container-lifecycle.cjs <private-container-verification.json> --cleanup
```

The container runs with a read-only filesystem and no external network access. Checks use synthetic Telegram/admin identities with production authentication enabled, wire-level host routing, and actual isolated PostgreSQL/Redis data. The lifecycle check temporarily disconnects Redis only from the owned verification network, restores connectivity in `finally`, checks readiness recovery, then stops/removes the owned runtime and network. PostgreSQL/Redis fixtures are retained. It does not send real Telegram messages or make purchases, refunds, voice connections, or storage uploads. Remote CI execution and production deployment remain unverified.
